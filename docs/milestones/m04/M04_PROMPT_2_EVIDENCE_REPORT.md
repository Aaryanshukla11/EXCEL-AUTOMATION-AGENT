## 2. Global Output Resource Limits & Truncation Telemetry

### 2.1 Multi-Tier Resource Limits

`GridSegmenter` independently enforces resource limits across four separate tiers to guarantee bounded memory and runtime even under adversarial workloads:

| Resource Tier | Configurable Parameter | Default Limit | Enforcement Mechanism | Overflow / Truncation Action |
| :--- | :--- | :--- | :--- | :--- |
| **Lookahead Window Depth** | `window_size` ($W$) | 50 rows | Flushes row buffer every $W$ rows | Bounded memory $O(W \cdot C)$ |
| **Concurrent Active Regions** | `max_active_regions` | 1,000 regions | Checked per sliding window transition | `lookahead_overflow_detected = True`; details logged in `lookahead_overflow_details` |
| **Lookahead Window Span** | `max_overflow_window_span` | 500 windows | Tracked per continuous active block | `lookahead_overflow_detected = True`; region span documented |
| **Separation Corridors** | `max_corridors` | 5,000 corridors | Checked during horizontal & vertical corridor cuts | Capped; `is_truncated = True`; details logged |
| **Finalized Table Regions** | `max_finalized_regions` | 5,000 regions | Checked during block finalization and classification | Capped; `is_truncated = True`; details logged |
| **Isolated Sparse Islands** | `max_sparse_islands` | 2,000 islands | Checked during sparse island accumulation | Capped; `is_truncated = True`; details logged |

### 2.2 Distinguishability of Complete vs. Truncated Results
- **`is_truncated` (bool)**: Emitted on `SpatialDetectionReport`. Evaluates to `False` for complete, untruncated runs and `True` whenever any resource ceiling (regions, islands, or corridors) is reached.
- **`truncation_details` (Optional[str])**: Provides human-readable descriptions of exact limits reached (e.g. `"Finalized regions reached output limit (5000); Corridors reached limit of 5000"`).
- **Non-Silent Capping**: The engine **never silently discards data**. Every truncation is explicitly flagged in both boolean flags and descriptive strings.

## 3. Streaming Interface & Pipeline Data Flow Audit

### 3.1 Reader Class & Data Path Trace
- **Reader Class**: `excel_intel.core.parser.StreamingWorkbookReader` (M02).
- **Streaming Method**: `reader.stream_sheet(sheet_name, chunk_size=1000)` yielding chunks of row dictionaries.
- **Data Path**:
  1. `StreamingWorkbookReader` delegates to native Rust `SheetChunkIterator` (`crates/excel_intel_rs/src/worksheet.rs`).
  2. The native Rust engine uses `quick-xml` to parse the worksheet XML stream directly from the OpenXML ZIP archive.
  3. Row records with cell coordinates and values (`{'row': int, 'cells': [{'col': int, 'value': Any}]}`) are yielded as Python dictionaries in batches of 1,000 rows.
  4. `GridSegmenter.segment_rows()` flattens chunk batches and extracts row indices and populated column indices into its sliding lookahead buffer.

### 3.2 XML Materialization Audit
- **In `GridSegmenter` Standalone Execution**:
  - **Verified Fact**: No worksheet XML is materialized as a Python string, and no Python DOM (`xml.etree.ElementTree`) is created anywhere during `GridSegmenter.segment_sheet()` or `GridSegmenter.segment_rows()`.
- **In Complete Pre-Inspection Pipeline (M03 Integration)**:
  - **Verified Fact**: If M03 `DeclaredOpenXmlFacts` are pre-generated by `WorkbookInspector.inspect()`, M03's package reader reads the worksheet XML part into a memory string for `ET.iterparse` to discover merge cells and hidden dimensions.
  - **Verified Distinction**: Total pipeline memory during pre-inspection is dominated by M03 XML part reading, whereas M04 `GridSegmenter` streaming operates with zero Python XML materialization.

## 4. Controlled Benchmark Evidence (Process-Isolated)

To eliminate process memory retention, allocator fragmentation, and cross-run caching, all benchmarks were executed in **isolated subprocesses** using `tests/benchmarks/run_m04_benchmarks.py`.

### 4.1 Benchmark Measurements

| Workload (Rows $\times$ Cols) | Layout | Time (s) | Baseline RSS | Peak RSS | Delta RSS ($\Delta$) | Regions Detected |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| **10,000 $\times$ 10** | **Dense** | 0.200 s | 18.99 MB | 31.28 MB | **+12.29 MB** | 1 region, 0 islands |
| **10,000 $\times$ 10** | **Sparse** | 0.333 s | 18.80 MB | 35.05 MB | **+16.25 MB** | 500 regions, 101 islands |
| **50,000 $\times$ 10** | **Dense** | 1.059 s | 19.04 MB | 31.20 MB | **+12.16 MB** | 1 region, 0 islands |
| **50,000 $\times$ 10** | **Sparse** | 6.349 s | 18.99 MB | 50.75 MB | **+31.75 MB** | 2,500 regions, 501 islands |
| **100,000 $\times$ 10** | **Dense** | 3.205 s | 19.01 MB | 31.12 MB | **+12.11 MB** | 1 region, 0 islands |
| **100,000 $\times$ 10** | **Sparse** | 21.663 s | 19.01 MB | 69.12 MB | **+50.11 MB** | 5,000 regions, 1,001 islands |

### 4.2 Empirical Observations & Memory Complexity
1. **Dense Workloads**:
   - For continuous tables spanning from 10,000 to 100,000 rows, **Peak RSS remains completely constant at ~31.1–31.3 MB** ($\Delta \approx 12.1\text{ MB}$).
   - This empirically confirms $O(W \cdot C)$ memory boundedness for streaming single-table workloads.
2. **Sparse Workloads**:
   - Peak RSS increases from 35.05 MB (10k rows) to 69.12 MB (100k rows) due to accumulating 6,001 distinct Pydantic region/island objects ($K$).
   - Even with 6,001 distinct regions retained in memory, peak memory (69.12 MB) remains far below the defensive 235 MB platform threshold.
3. **Qualified Complexity Formulation**:
   - Sliding lookahead buffer memory is strictly **$O(W \cdot C)$**.
   - Total report retention memory scales as **$O(W \cdot C + K)$**, where $K$ is bounded by $\min(\text{actual regions}, \text{max\_finalized\_regions} + \text{max\_sparse\_islands})$.

## 5. M01 Compatibility & Bridge Verification

### 5.1 Preservation of Fields
The bridge method `SpatialTableRegion.to_table_metadata()` performs lossless field-level conversion to M01 `TableMetadata`:
- `bounding_box.min_row` $\rightarrow$ `bounding_box.start_row`
- `bounding_box.min_col` $\rightarrow$ `bounding_box.start_col`
- `bounding_box.max_row` $\rightarrow$ `bounding_box.end_row`
- `bounding_box.max_col` $\rightarrow$ `bounding_box.end_col`
- `sheet_name` $\rightarrow$ `sheet_name`
- `header_row` $\rightarrow$ `header_row`
- `columns` $\rightarrow$ `columns` (including `inferred_type`, `type_confidence`, `header_name`, `index`)
- `is_declared` $\rightarrow$ `is_list_object`
- `declared_name` $\rightarrow$ `list_object_name`

### 5.2 Strict Non-Fabrication Guard
- **Verified Fact**: If `header_row` or `columns` are `None` (unresolved in Prompt 2), `to_table_metadata()` raises `NotImplementedError`.
- **Non-Fabrication Policy**: The engine explicitly refuses to fabricate placeholder column types or dummy header row indices.

## 7. Categorized Invariant & Evidence Matrix

### 7.1 Verified Facts
- `GridSegmenter` streams rows without materializing complete worksheet XML in Python.
- M01 (`excel_intel/core/`) and M02 (`crates/excel_intel_rs/`) production code are 100% frozen and unmodified.
- Lookahead window row buffer flushes completely every $W=50$ rows.
- Source workbook SHA-256 checksums are unchanged before and after segmentation.
- Concurrent execution across 4 threads produces deterministic, non-contaminated results.
- Global output limits (`max_finalized_regions`, `max_sparse_islands`, `max_corridors`) truncate gracefully and surface explicit boolean and text telemetry.

### 7.2 Empirical Observations
- Dense streaming memory delta is constant ($\approx 12.1\text{ MB}$) from 10k to 100k rows.
- Sparse streaming memory scales with $K$, the number of distinct regions/islands, reaching 69.12 MB for 6,001 objects.
- All test suites execute in $< 10\text{ seconds}$ across Rust, Python 3.12, and Python 3.13.

### 7.3 Heuristic Behavior
- Inferred table candidate scores are computed via transparent heuristics based on density and corridor isolation:
  $$\text{Confidence} = \min(1.0, 0.50 \cdot \text{density} + 0.50)$$
- Declared OpenXML tables receive heuristic confidence $1.0$ representing certainty of declaration, not semantic correctness.
- Scores are clamped to $[0.0, 1.0]$ and are explicitly non-calibrated.

### 7.4 Assumptions
- Worksheets conform to the OpenXML coordinate grid ($1 \le \text{row} \le 1,048,576$, $1 \le \text{col} \le 16,384$).
- Row records yielded by the reader are sorted monotonically by row index.

### 7.5 Unverified Limitations (Deferred to Prompt 3 & Prompt 4)
- **Multi-Row / Hierarchical Headers**: Unresolved; reserved for M04 Prompt 3 Header Resolution Engine.
- **Semantic Zone Classification**: Unresolved; reserved for M04 Prompt 4 Semantic Zone Classifier.
- **Column Data Type Inference**: Not performed in Prompt 2; reserved for type inference integration.
